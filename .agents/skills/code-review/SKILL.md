# Ревью кода

Найди доказанные дефекты в запрошенной области и дай итог, соответствующий
покрытию и доказательствам. Глубину определяют затронутые контракты и риск,
а не размер отчёта. Ревью само по себе не разрешает исправлять код, тесты или owners.

## Область и глубина

- Для изменений или PR установи базу сравнения и состав diff. При ревью текущей
  рабочей копии учитывай staged, unstaged и относящиеся к задаче untracked файлы.
  Проверяй изменённое поведение и связи, через которые оно может вызвать регрессию.
- Для аудита фазы или проектной области проверяй весь заявленный контракт,
  включая реализацию вне diff. До итогового verdict определи покрытие существенных
  границ: состояние/schema, owner, запись/transaction, публичный контракт,
  consumers/UI, verification — только применимые к объекту.
  Если область охватывает несколько границ или owners, используй краткую матрицу
  «граница → ожидаемое правило → доказательство → результат/пробел» в отчёте.
  Для локального ревью отдельная матрица не нужна.
- При повторном ревью используй прежние IDs и критерии; проверяй исправления и
  риски их нового diff. Не переоткрывай незатронутые доказанные результаты.
  Новые доказанные дефекты допускаются; явно отделяй их от незакрытых прежних.

Нельзя выдавать проверку части области за аудит целого проекта. Если база или
scope неясны, сначала используй доступный контекст; один точечный вопрос нужен,
когда неоднозначность меняет контракт, область или критерии приёмки.

## Контекст и проверка

Используй Session Router проекта: owning doc или contract фазы, фактическую
реализацию и применимые `INV-*`. При противоречии документа и кода установи
ожидаемый контракт; текущая реализация сама по себе не доказывает корректность.
Этот skill не заменяет доменные правила, команды и документацию стека.

Для каждого изменённого поведения проследи достижимый путь до результата.
При изменении общего или публичного контракта проверь прямых потребителей;
следуй дальше только по конкретной зависимости или риску. По применимости
проверь failure paths, авторизацию, sensitive output, транзакции и повторные
side effects, совместимость данных, UI-сценарии и ограниченность запросов.
Не превращай этот список в обязательный обход незатронутых областей.

Когда контракт, нарушающий путь, потребители и достаточная проверка известны,
переходи к выводу. Расширяй чтение для конкретного неизвестного, противоречия
или нового риска; не перечитывай owners и неизменённые файлы без причины.

Выбирай минимально достаточный gate для проверяемого свойства. Статический
разбор, один regression-тест или сценарий могут быть достаточны, если покрывают
нарушающий путь и затронутые границы. Не добавляй проверки ради количества.
Full suite нужен при широком риске, закрытии этапа или требовании проекта/пользователя.
Не повторяй успешный gate при неизменных проверяемых коде, данных и среде;
используй имеющиеся подтверждения только с известной областью и актуальными входами.
Проверки выполняй без изменения production-данных; секреты не читай и не выводи.

## Порог дефекта

Finding требует цепочки: **контракт → достижимый нарушающий путь → наблюдаемый эффект**.
Подтверждением могут быть код и фактические связи либо воспроизводимый сценарий;
runtime-запуск обязателен, когда без него существенное звено остаётся неизвестным.
Приведи точный `file:line` и условия возникновения. Для заявления о регрессии
покажи связь с изменением; существующие дефекты отмечай отдельно.

Предпочтение иной реализации, необязательное усиление, недостижимый крайний
случай и один отсутствующий тест сами по себе не являются дефектами.
Существенную гипотезу проверь минимальным способом, способным её опровергнуть.
Отклонённую гипотезу не открывай снова без нового evidence; перебор догадок
не включай в findings. Непроверенное существенное условие укажи как ограничение
покрытия и учти в verdict, не выдавая его за установленный дефект.

Отсутствие обязательного подтверждения — пробел проверки, а не доказательство
сломанного поведения. Ложное заявление о выполненной проверке или закрытии
может быть самостоятельным доказанным нарушением контракта завершения.
Тест или валидатор подтверждает только проверяемое им свойство.

Уровни: `BLOCKER` — критическое нарушение, блокирующее принятие;
`MAJOR` — существенный дефект, требующий исправления до принятия;
`MINOR` — доказанный локальный дефект. Стиль и необязательные улучшения
не получают severity и не меняют verdict.

## Возможности упрощения

Показывай только обоснованные предложения из live evidence в запрошенной области:
необязательный механизм, ненужная прослойка или подтверждённый overlap.
Для необходимости новой конструкции используй [INV-REUSE-1]invariants.md#registry.
Укажи место, что заменить или убрать, существующий вариант/reference и как
сохранить контракт и обязательные boundaries. Малое число строк, один caller
или implementation и личный стиль сами по себе не основания для предложения.
Необязательные предложения отделяй от defect findings; не назначай severity
и не меняй verdict. Доказанное нарушение обязательного контракта оценивай
по существующему порогу дефекта. Отдельный reviewer, аудит или дополнительный
обход всего repo не нужны; выводи только найденные обоснованные предложения.
Предложение упрощения не разрешает remediation.

## Исправления и повторное ревью

Если исправления отдельно разрешены, сначала зафиксируй findings и критерии
их закрытия. Затем используй обычный маршрут реализации проекта без отдельной
обязательной карточки или нового процесса. Сохрани scope и существующего owner.

Изменённый код сам по себе не закрывает finding. Проверь устранение нарушающего
пути, затронутых потребителей и сохранённое поведение с актуальными доказательствами.
Если подтверждения недостаточны, отметь «исправлено, не подтверждено».
Новый контракт согласуй как изменение scope; не подменяй им критерий прежнего дефекта.
Документационный дефект допускает статическое закрытие; документация или
общий валидатор не доказывают исправление runtime-поведения.

## Результат

Пиши по-русски. Сначала findings по серьёзности: место, условие возникновения,
нарушенный контракт и эффект. Затем кратко область/база, проверки и ограничения,
один verdict. Успешная команда: команда, exit code и значимый count;
неуспешная: причина и короткий релевантный лог. Если дефектов не найдено,
скажи это прямо, сохранив существенные ограничения проверки.

- `PASS` — область покрыта достаточно, доказанных дефектов и существенных
  пробелов обязательной проверки нет; это не заявление о непроверенном runtime.
- `NEEDS FIXES` — есть доказанные дефекты; укажи их количество по severity.
- `PARTIAL` — выполнена полезная часть проверки, но существенная область или
  обязательный gate остались непроверенными.
- `INCONCLUSIVE` — недостаточно данных для обоснованного итога по объекту.

Если есть дефекты и пробелы одновременно, используй `NEEDS FIXES` и укажи
ограничения. При повторном ревью сообщи закрытые, оставшиеся и новые findings.

Для обычного ревью выдавай findings в чат; файл не обязателен. Для широкого
аудита проекта/фазы или явного запроса на документ сохрани результат в
`docs/audits/<audit-key>.md` либо указанном пользователем месте. По объекту
и стабильному тематическому ключу найди существующий аудит и обнови тот же файл;
не создавай dated copies без запроса. Артефакт хранит scope/базу, покрытие,
findings с доказательствами, ограничения, проверки и итог; ссылайся на owners
вместо копирования контрактов. В чат верни ключевые findings, итог и ссылку.
При запрете записи отвечай в чат; при ошибке записи явно сообщи её.
